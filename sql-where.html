01 The Story 4 min read

SELECT shows you everything. That's the problem.

You're a freshly hired data analyst. First task from your manager: "Pull everyone from Delhi with a score above 75."

You've just learned SELECT. You run SELECT * FROM students; — five rows drop on screen. You read each one. You compare. You mentally cross out Priya (Mumbai), Raj (Pune), Karan (Chennai), Simran (score: 61). You find Arjun. Done.

Now imagine that table has 10,000 rows. Then 500,000. Then 10 million. The manual-scan approach collapses at row 21.

WHERE is what you were missing. One extra line, and the database does all the scanning for you — instantly, on any size table.
How it works
WHERE evaluates every row, one at a time. For each row, it asks: "Does this row pass my condition?" If the answer is TRUE → the row is included in your results. If the answer is FALSE or NULL → the row is silently dropped. That's the entire mechanism.

02 Why it matters 3 min read

Real tables don't have 5 rows.

Every production database you'll encounter in a job has tables with thousands, millions, even billions of rows. No analyst, no application, no dashboard ever reads all of them. Every real SQL query filters.

Industry reality
In data analytics roles, over 85% of SQL queries contain a WHERE clause. It's not advanced SQL — it's the baseline. A query without WHERE is a table dump, not analysis. WHERE is what makes SQL useful for answering business questions.

Think about what every real question sounds like:

Business questions → SQL WHERE clauses
-- "Show me customers from Mumbai"
WHERE city = 'Mumbai'

-- "Sales above ₹50,000 this quarter"
WHERE amount > 50000

-- "Users who haven't logged in for 30 days"
WHERE last_login < '2024-01-01'

-- "Products that are out of stock"
WHERE stock = 0 OR stock IS NULL
Safe like SELECT
WHERE only controls which rows you read. It never modifies data. Like SELECT, you can run any WHERE query anywhere, any number of times — it is completely safe.

NULL Checks
IS NULL
Value is missing
The only correct way to check for NULL. = NULL does not work.
score IS NULL
IS NOT NULL
Value exists
Returns rows that have an actual value in the column.
score IS NOT NULL

The NULL trap — this catches everyone at least once:

Wrong — returns 0 rows silently
WHERE score = NULL
NULL can't be compared with =. In SQL, NULL = NULL evaluates to NULL (not TRUE). This query matches nothing — no error, just empty results.
Correct — use IS NULL
WHERE score IS NULL
IS NULL is the dedicated NULL check. It correctly finds rows where score has no value stored. Pair with IS NOT NULL to find rows that do have a value.

⚠ AND runs before OR — parentheses control grouping

SQL evaluates AND before OR, the same way multiplication runs before addition in math. Without parentheses, this causes silent logic errors:

Ambiguous — AND groups first
WHERE city = 'Delhi' OR city = 'Mumbai' AND score > 70
Reads as: Delhi OR (Mumbai AND score>70). All Delhi rows pass regardless of score — Simran (61) slips through.
Explicit — parentheses lock intent
WHERE (city = 'Delhi' OR city = 'Mumbai') AND score > 70
Now AND applies to both cities. Only Delhi/Mumbai students with score above 70 pass. Simran (61) is correctly excluded.

You just joined ShopNest — India's newest e-commerce startup — as their first data analyst. The product catalog has 10,000 SKUs and zero consistency. Product names were entered by 12 different vendors. SKUs follow a loose pattern. Nobody agreed on anything.

Task 3 Apple OR Samsung only — for a comparison report
Rahul says: "Apple and Samsung only. The investor wants a head-to-head comparison. Two brands, one query."

SQL Server has no REGEXP keyword — no | alternation. The SQL Server way is explicit OR conditions: one LIKE per prefix. Clear, readable, and index-friendly.

MySQL/PostgreSQL — REGEXP alternation
WHERE sku REGEXP '^(APL|SAM)'
REGEXP with | alternation is MySQL/PostgreSQL syntax. SQL Server has no REGEXP keyword — this query errors out on SQL Server.
LIKE + OR — SQL Server native
WHERE sku LIKE 'APL%'
OR  sku LIKE 'SAM%'
One LIKE per prefix, joined with OR. Add OnePlus: OR sku LIKE 'OPL%'. Each condition can use a separate index — often faster than REGEXP anyway.

Rahul says: "Our SKU format should be 3 uppercase letters, then a hyphen, then more stuff. The HP product is using 2 letters — 'HP-'. Find any SKU that doesn't follow the 3-letter standard so we can flag it."

You need SKUs that do not start with exactly 3 uppercase letters followed by a hyphen. SQL Server LIKE supports [A-Z] character ranges — write it three times for three positions.

Basic LIKE _ — counts but can't check case

WHERE sku NOT LIKE '[A-Z][A-Z][A-Z]-%'

04b Reference Extras

Write faster queries — know your operators' cost

Performance and portability reference. These two tables are what senior engineers keep pinned.

Performance Tips & Operator Cost
= / != / > / <
Fastest
Exact comparisons use b-tree indexes. Always prefer these when you know the value.
Use when: filtering by exact ID, status, number, or known text value.
IN / BETWEEN
Fast
IN on a short literal list is index-friendly. BETWEEN uses a range scan. Both very efficient.
Use when: matching a short list of values or a numeric / date range.
LIKE 'A%'
Fast (prefix)
Wildcard at the end only — the optimizer can use the b-tree from the known prefix forward.
Use when: names starting with A, codes starting with APL-, dates starting with 2024-.
LIKE '%A%'
Full scan
Leading wildcard forces a full table scan — every row is checked. Fine on small tables.
Avoid on large tables. SQL Server: use CONTAINS(col, 'term') with a Full-Text Index. MySQL: MATCH…AGAINST.
LIKE '[A-Z]%'
Full scan
SQL Server LIKE with character classes ([A-Z], [0-9]) always scans all rows — no index benefit. Fast on small tables.
Avoid in production hot-paths on large tables. Pre-process into structured columns.
IN (subquery)
Depends
Inner query runs first. On large result sets, EXISTS is often faster — it short-circuits on the first match.
Prefer EXISTS for existence checks. Use IN when you need the actual values returned.

EXISTS takes a subquery and asks one question: does this subquery return at least one row? If yes, the outer row passes. If no, it's filtered out. It's perfect for relationship questions: "find me all X that have at least one Y." Here we find every employee who is listed as someone else's manager.

    FROM Employees e2

Real-world pattern — data quality filtering

Production data is rarely clean. A common task: find rows where a column is missing, then display a fallback. IS NULL finds the gaps; COALESCE fills them in the output.

SQL — SQL Server 
-- Find students missing a city, display 'Unknown' instead of NULL
SELECT name,
       COALESCE(city, 'Unknown') AS city,
       score
FROM students
WHERE city IS NULL
   OR city = '';
Two-part pattern: WHERE city IS NULL OR city = '' catches both true NULLs and accidental empty strings (both mean “no data entered”). COALESCE(city, 'Unknown') swaps NULL for a readable label in the results — the underlying data is unchanged. In SQL Server, ISNULL(city, 'Unknown') is an equivalent shorthand for the two-argument case.
06 Common Mistakes 4 min read

Ten traps — every beginner hits at least three.

WHERE score = NULL — the silent trap
This returns 0 rows with no error. NULL cannot be compared with =. SQL evaluates NULL = NULL as NULL (not TRUE), so nothing matches. Always use IS NULL or IS NOT NULL.
Missing quotes around text values
WHERE city = Delhi throws an error because SQL thinks Delhi is a column name. Always wrap text values in single quotes: WHERE city = 'Delhi'. Numbers need no quotes: WHERE score = 80.
Using == (Python habit) instead of =
WHERE score == 80 is invalid SQL. SQL equality is single =. Double == is Python and JavaScript. This one bites almost every developer switching to SQL for the first time.
BETWEEN 70 TO 90 — wrong connector
The connector inside BETWEEN is AND, not TO. BETWEEN 70 TO 90 is a syntax error. Think of it as: "score is between 70 AND 90." Always: BETWEEN low AND high.
AND is stricter, OR is more permissive
AND requires every condition to pass — fewer rows come through. OR only needs one condition to pass — more rows come through. Confused? Ask yourself: "am I narrowing down or expanding the results?" That's AND vs OR.
Each condition needs its own column name
WHERE city = 'Delhi' AND = 'Mumbai' is broken. SQL doesn't inherit the column from the previous condition. Write it in full: WHERE city = 'Delhi' OR city = 'Mumbai'. Or cleaner: WHERE city IN ('Delhi','Mumbai').
NOT IN with a NULL in the list — silent zero rows
WHERE city NOT IN ('Delhi', NULL) returns 0 rows with no error. SQL can never confirm that any value is "not equal to NULL" — the comparison resolves to NULL (unknown), which evaluates as FALSE. If NULLs may exist, filter them separately with IS NOT NULL.
AND/OR precedence — AND groups first without parentheses
WHERE city='Delhi' OR city='Mumbai' AND score>70 is not what it looks like. SQL runs the AND first: it becomes Delhi OR (Mumbai AND score>70). Simran from Delhi (score 61) still passes. Fix: add parentheses — WHERE (city='Delhi' OR city='Mumbai') AND score>70.
LIKE without a wildcard behaves like = in SQL Server
In SQL Server, both = and LIKE are case-insensitive under the default collation, so WHERE name = 'arjun' and WHERE name LIKE 'arjun' return the same rows. The real difference: LIKE supports wildcard patterns (%, _, []); = matches the exact value only. Use = for exact-value lookups (it's slightly faster and intent is clearer) and LIKE whenever you need pattern matching.
WHERE cannot filter aggregates — that's HAVING's job
This is the #1 confusion when you first meet GROUP BY. WHERE runs before grouping — it filters individual rows. Aggregates like COUNT(*) don't exist yet at that point. Moving the filter after grouping is exactly what HAVING is for.
❌ Broken
SELECT Department,
  COUNT(*)
FROM Employees
WHERE COUNT(*) > 3
GROUP BY Department;
Error: aggregate not allowed in WHERE
✅ Fixed
SELECT Department,
  COUNT(*)
FROM Employees
GROUP BY Department
HAVING COUNT(*) > 3;
HAVING filters after grouping
Memory hook: WHERE = "filter the rows going IN to the group." HAVING = "filter the groups coming OUT." You'll learn GROUP BY and HAVING on the next page — but knowing this distinction now saves hours of confusion later.
NULL arithmetic silently poisons comparisons — use COALESCE
Any arithmetic with NULL returns NULL, so salary + bonus > 80000 silently skips rows where bonus is NULL. The row doesn't fail the filter — it's just invisible. COALESCE substitutes a default value so no rows are lost.
❌ Silently drops NULLs
-- Employees with NULL bonus
-- are quietly excluded
SELECT Name, Salary, Bonus
FROM Employees
WHERE Salary + Bonus > 80000;
NULL + anything = NULL → WHERE sees NULL → row excluded
✓ NULL-safe with COALESCE
-- Treat NULL bonus as 0
SELECT Name, Salary, Bonus
FROM Employees
WHERE Salary + COALESCE(Bonus, 0)
     > 80000;
COALESCE(Bonus, 0) → NULL becomes 0, no rows lost
NULLIF bonus: NULLIF(value, 0) goes the other direction — turns a 0 into NULL (useful to avoid divide-by-zero). Together: COALESCE(col, fallback) = “use fallback if NULL” · NULLIF(col, val) = “return NULL if col equals val.”
07 Key Takeaways 2 min read

What you just learned.

Quick Reference WHERE — what you need to know
  • WHERE goes after FROM and filters rows. Only rows where the condition is TRUE appear in the result.
  • Every condition has 3 parts: column — operator — value. If one is missing, that's your bug.
  • Text values need single quotes ('Delhi'). Numbers do not (80). Forgetting quotes is the #1 beginner error.
  • Never use = NULL. It silently returns 0 rows. Use IS NULL or IS NOT NULL.
  • AND = both conditions required (stricter, fewer rows). OR = either condition sufficient (more permissive, more rows).
  • BETWEEN includes both endpoints. BETWEEN 70 AND 90 is the same as >= 70 AND <= 90.WHERE score BETWEEN 70 AND 90
  • IN is cleaner than multiple ORs. city IN ('Delhi','Mumbai') is easier to read than city = 'Delhi' OR city = 'Mumbai'.
  • WHERE never changes data. Like SELECT, it only reads. Safe to run anywhere, any number of times.
  • SQL Server's LIKE operator supports [A-Z], [0-9], [AP] character classes — its hidden superpower. Write [A-Z][A-Z][A-Z] instead of REGEXP's [A-Z]{3}. Use LEN() for exact length checks, and PATINDEX() for pattern position searches.
  • NOT BETWEEN and NOT LIKE invert their operators exactly. score NOT BETWEEN 70 AND 90 returns scores below 70 or above 90.
  • Date filtering works with text comparison when dates are stored as YYYY-MM-DD. Use >, BETWEEN, and LIKE '2022-%' — no special functions needed. In SQL Server with typed DATE/DATETIME columns, use YEAR(col) = 2022 or col >= '2022-01-01' AND col < '2023-01-01' — avoids the midnight trap on DATETIME ranges.
  • Subqueries in WHERE run first and pass a value to the outer query. WHERE Salary > (SELECT AVG(Salary) FROM Employees) always uses the current average — no hardcoded numbers.
  • The _ wildcard matches exactly one character. LIKE '_r%' means: any first character, then r, then anything. Combine _ and % to target specific positions precisely.
  • EXISTS checks for the presence of a related row, not a value. WHERE EXISTS (SELECT 1 FROM … WHERE condition) is TRUE if the subquery returns even one row — use it for "has at least one" questions.
  • WHERE cannot use aggregate functions. WHERE COUNT(*) > 3 is an error. WHERE filters individual rows before grouping. Use HAVING to filter the results of GROUP BY — that's the one job WHERE cannot do.

10 Interview Prep 5 min read

10 questions interviewers love to ask about WHERE.

Click any card to reveal the answer. These surface the why behind the syntax — the part most candidates miss.

Concept Trap Pattern Advanced

Trap What does WHERE name = NULL return — and why?
It returns zero rows, always — even if the column contains NULLs.
-- Returns 0 rows, not the NULLs
SELECT * FROM Employees WHERE Manager = NULL;

-- Correct: use IS NULL
SELECT * FROM Employees WHERE Manager IS NULL;
Why: NULL means "unknown". Comparing unknown to anything — even another unknown — is itself unknown, not TRUE. SQL’s three-valued logic (TRUE / FALSE / UNKNOWN) means = NULL always evaluates to UNKNOWN, which WHERE treats as "don’t include this row". IS NULL is a special predicate that specifically checks for the absence of a value.
Interviewer follow-up: "What about WHERE col != NULL?" — same answer: also returns nothing. Always use IS NOT NULL.
Concept What is the difference between WHERE and HAVING?
WHERE filters individual rows before grouping. HAVING filters groups after GROUP BY. WHERE cannot reference aggregates; HAVING can.
-- WHERE: filter rows before grouping
SELECT Department, COUNT(*) AS cnt
FROM Employees
WHERE HireYear >= 2020 -- row-level filter
GROUP BY Department
HAVING COUNT(*) > 2; -- group-level filter
Execution order: FROM → WHERE (filters rows) → GROUP BY → HAVING (filters groups) → SELECT → ORDER BY. WHERE runs at step 2; aggregates don’t exist yet at that point, which is exactly why you can’t use COUNT(*) in WHERE.
Memory hook: WHERE = "rows going IN to the group." HAVING = "groups coming OUT."
Pattern When should you use IN vs EXISTS?
Use IN for a short literal list or when you need the actual values. Use EXISTS when checking whether a related row exists — it short-circuits on the first match and is often faster on large datasets.
-- IN: good for small, known lists
WHERE Department IN (‘Sales’, ‘IT’, ‘Finance’)

-- EXISTS: better for large subqueries (short-circuits)
WHERE EXISTS (
  SELECT 1 FROM Orders o
  WHERE o.EmployeeID = e.EmployeeID
)
Critical trap with IN + subquery: If the subquery returns even a single NULL, WHERE col NOT IN (subquery) returns zero rows — because col != NULL is UNKNOWN. EXISTS doesn’t have this problem.
Rule of thumb: If the list could contain NULLs, prefer EXISTS over NOT IN. Always.
Trap What happens to NULL values in WHERE col NOT IN (...) when the list contains a NULL?
The entire query returns zero rows — a silent, devastating bug that’s easy to miss in production.
-- List contains a NULL → returns 0 rows, always
SELECT * FROM Employees
WHERE EmployeeID NOT IN (1, 2, NULL);

-- Why: NOT IN expands to:
-- EmployeeID != 1 AND EmployeeID != 2 AND EmployeeID != NULL
-- The last condition is UNKNOWN → whole AND is UNKNOWN → excluded
Fix: Filter NULLs from the subquery: WHERE col NOT IN (SELECT id FROM t WHERE id IS NOT NULL). Or switch to NOT EXISTS, which handles NULLs safely by design.
Interview answer pattern: Mention three-valued logic, explain AND UNKNOWN = UNKNOWN, then give the fix. This shows depth.
Concept Explain the execution order of SQL clauses.
SQL clauses execute in this logical order, regardless of how you write them:
1. FROM / JOIN / ON — build the initial row set
2. WHERE — filter individual rows
3. GROUP BY — group remaining rows
4. HAVING — filter groups
5. SELECT — compute output columns
6. DISTINCT — deduplicate
7. ORDER BY — sort
8. LIMIT / OFFSET — paginate
Why this matters: SELECT aliases aren’t available in WHERE (SELECT runs after WHERE). Aggregates aren’t available in WHERE (SELECT runs after WHERE). You can’t ORDER BY without GROUP BY covering it in some databases. Understanding this order explains almost every "why doesn’t this work?" SQL error.
Memory sentence: "From Join Where Group Having Select Order Limit" — "Friendly John Went Golfing, Having Sunk One Last putt."
Pattern What’s the performance difference between LIKE ‘%text%’ and LIKE ‘text%’?
LIKE ‘text%’ (suffix wildcard) can use a b-tree index — fast. LIKE ‘%text%’ (leading wildcard) forces a full table scan — slow at scale.
-- FAST: index can scan from ‘text’ forward
WHERE name LIKE ‘John%’

-- SLOW: must check every row character by character
WHERE name LIKE ‘%ohn%’

-- At scale: use full-text search (MATCH AGAINST, pg_trgm)
-- for "contains" queries on large tables
Why leading wildcards kill indexes: A b-tree index stores values in sorted order. "Starts with X" means "look from X onwards" — the index handles it. "Contains X anywhere" means there’s no known starting position — the engine must read every row.
SQL Server production tip: For "contains X" on large tables, use Full-Text Search: CREATE FULLTEXT INDEX ON Products(name), then WHERE CONTAINS(name, 'Pro'). Far faster than LIKE '%Pro%'. MySQL uses FULLTEXT + MATCH...AGAINST; PostgreSQL uses pg_trgm GIN index.
Pattern Is BETWEEN a AND b inclusive or exclusive of the boundary values?
BETWEEN is always inclusive on both ends. BETWEEN 80 AND 90 is exactly equivalent to >= 80 AND <= 90.
-- These are identical:
WHERE score BETWEEN 80 AND 90
WHERE score >= 80 AND score <= 90

-- Date trap: this EXCLUDES ‘2024-12-31’ records after midnight
WHERE hire_date BETWEEN ‘2024-01-01’ AND ‘2024-12-31’
-- Safer for datetimes:
WHERE hire_date >= ‘2024-01-01’ AND hire_date < ‘2025-01-01’
Date/datetime trap: BETWEEN ‘2024-01-01’ AND ‘2024-12-31’ on a DATETIME column excludes records where the time portion is after midnight on Dec 31. Use < ‘2025-01-01’ instead to capture the full day.
One more catch: Make sure a <= b. BETWEEN 90 AND 80 returns zero rows in most databases.
Trap What’s wrong with: WHERE city=’Delhi’ OR city=’Mumbai’ AND score > 70?
AND has higher precedence than OR, so this reads as city=’Delhi’ OR (city=’Mumbai’ AND score > 70) — returning all Delhi rows regardless of score.
-- Actual behavior (AND binds first):
WHERE city=’Delhi’ -- ALL Delhi students
OR (city=’Mumbai’ AND score > 70) -- Only Mumbai >70

-- What was likely intended:
WHERE (city=’Delhi’ OR city=’Mumbai’) AND score > 70

-- Or cleaner:
WHERE city IN (‘Delhi’,’Mumbai’) AND score > 70
Operator precedence in SQL: NOT > AND > OR. Always parenthesize when mixing AND and OR. This is one of the most common WHERE bugs in production code.
Defensive habit: Any time you write OR next to AND, add parentheses — even when you think they’re not needed. Future-you will thank present-you.
Advanced What is a correlated subquery, and how does it differ from a regular subquery?
A regular subquery runs once. A correlated subquery runs once per outer row because it references a column from the outer query.
-- Regular subquery: runs ONCE
SELECT Name FROM Employees
WHERE Salary > (SELECT AVG(Salary) FROM Employees);

-- Correlated subquery: runs for EVERY outer row
SELECT e1.Name, e1.Department
FROM Employees e1
WHERE EXISTS (
  SELECT 1 FROM Employees e2
  WHERE e2.ManagerID = e1.EmployeeID -- references outer e1
);
Performance implication: On a table with 10,000 rows, a correlated subquery in WHERE could execute 10,000 times. Modern optimizers often rewrite them, but not always. On large datasets, prefer JOIN or a CTE over correlated subqueries.
Spot the correlation: If the subquery references a column from the outer query’s table alias, it’s correlated. The keyword EXISTS almost always signals a correlated subquery.
Concept How do you filter rows in a JOIN — ON clause or WHERE clause? Is there a difference?
For INNER JOIN, the result is the same. For OUTER JOINs (LEFT/RIGHT), it’s critically different.
-- INNER JOIN: these are equivalent
FROM A JOIN B ON A.id = B.aid AND B.status = ‘active’
FROM A JOIN B ON A.id = B.aid WHERE B.status = ‘active’

-- LEFT JOIN: DIFFERENT behavior
-- ON clause: keeps all A rows; unmatched B cols are NULL
FROM A LEFT JOIN B ON A.id = B.aid AND B.status = ‘active’

-- WHERE clause: turns LEFT JOIN into INNER JOIN
FROM A LEFT JOIN B ON A.id = B.aid
WHERE B.status = ‘active’ -- NULLs fail this → rows dropped
The key difference: ON filters during the join (before unmatched rows are added back). WHERE filters after the join. On a LEFT JOIN, WHERE conditions on the right table eliminate the NULL-padded rows, effectively converting the LEFT JOIN to an INNER JOIN.
Rule: Join conditions belong in ON. Row filters after the join belong in WHERE. For outer joins, put right-side filters in ON unless you actually want to exclude non-matching left rows.

Lesson Coming Up · GROUP BY + HAVING
WHERE filters rows. HAVING filters groups.
GROUP BY collapses rows into summaries (counts, totals, averages). WHERE runs before that collapse — it picks which rows enter the group. HAVING runs after — it picks which groups survive.
SELECT Department, COUNT(*)
FROM Employees
WHERE IsActive = 1            -- WHERE: filter rows first
GROUP BY Department
HAVING COUNT(*) > 3;     -- HAVING: filter groups after
You already understand WHERE's role here — HAVING is its partner that works on the other side of the GROUP BY.
Lesson Coming Up · JOINs + ON
ON connects tables. WHERE still filters rows.
JOINs combine rows from two tables. The ON clause defines how they connect (like a foreign key link). WHERE still does exactly what you know — it filters the already-joined result. In OUTER JOINs, putting a filter in ON vs WHERE can change how many rows survive.
SELECT e.FirstName, d.DeptName
FROM Employees e
JOIN Departments d
  ON e.Department = d.DeptCode  -- connect
WHERE e.IsActive = 1;              -- filter
Everything you learned about WHERE — operators, NULLs, LIKE, subqueries — works identically in a JOIN query.
Lesson Coming Up · ORDER BY + LIMIT
WHERE picks the rows. ORDER BY ranks them.
WHERE decides which rows appear. ORDER BY decides the order they appear in. LIMIT caps the count. These three together answer "show me the top 5 highest-paid IT employees" — a query you'll write in five minutes once you know ORDER BY.
SELECT FirstName, Salary
FROM Employees
WHERE Department = 'IT'       -- WHERE you know
ORDER BY Salary DESC          -- new
LIMIT 5;                         -- new
One new clause at a time. You already own the hardest part.
